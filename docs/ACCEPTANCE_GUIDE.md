# DataBench 开发自查与提交检查指南

## 1. 这套工具解决什么问题

`python -m pytest` 用来判断公共接口和已有功能有没有被破坏，但“测试全部通过”不等于某个学生模块已经完成。未开发模块的占位页面也能通过基础页面测试。

`tools/acceptance.py` 解决的是另一类问题：它要求学生模块使用小型样例真实运行算法，生成 `AlgorithmResult` 和实验 JSON，再检查页面、文档、测试和数据材料是否达到相应提交要求。

文档中使用以下术语：

| 术语 | 含义 |
| --- | --- |
| 测试 | Pytest 中的单个自动化案例，验证一项具体代码行为。 |
| 检查项 | 验收器针对模块执行的一项判断，例如“算法文件存在”或“实验 JSON 字段完整”。 |
| 自动门禁 | 汇总所有自动检查结果。任何必需检查失败时输出 `BLOCKED`，全部通过时输出 `PASS`。 |
| 人工复核 | 工具无法可靠判断的内容，例如数据许可是否真实、页面解释是否清楚、指标结论是否夸大。 |

门禁不是评分算法，也不会替代教师或研究生评审。它只负责阻止明显不完整、不可运行或不符合接口的提交进入统一平台。

## 2. 三种检查模式

### 开发自查 `development`

用于日常开发和首次提交。重点回答：“模块是不是已经脱离占位状态，能否用小数据真实跑通？”

```powershell
python tools\acceptance.py --profile development --module error_detection
```

主要要求：真实页面、算法文件、模块 README、正常与错误输入测试、验收入口、小型样例、合法结果、实验 JSON 和安全文件。

### 中期提交检查 `midterm`

用于提交第一个端到端可运行版本。重点回答：“至少一种基础方法能否从输入一直运行到结果与实验记录？”

```powershell
python tools\acceptance.py --profile midterm --module error_detection
```

除开发自查内容外，还要求至少一种可运行方法，以及正常输入、错误输入、结果合同和实验保存四类测试。

### 最终提交检查 `final`

用于课程最终提交。重点回答：“两种方法、数据说明、实验比较和局限性是否齐全？”

```powershell
python tools\acceptance.py --profile final --module error_detection
```

除中期提交内容外，还要求至少两种不同方法或实验策略、模块级 `DATASET_CARD.md`，以及 README 中的指标和失败案例说明。

不指定 `--module` 时会检查全部 8 个模块：

```powershell
python tools\acceptance.py --profile development --label weekly_check
```

## 3. 学生需要提供的验收入口

每组在 `modules/<module_id>/acceptance.py` 提供：

```python
def run_acceptance(output_dir: Path) -> AcceptanceEvidence:
    ...
```

该函数必须：

1. 加载一个不依赖网络的小型样例。
2. 真实运行本组方法，不能只构造一份写死的结果。
3. 返回一个或多个通过 `validate()` 的 `AlgorithmResult`。
4. 使用 `save_experiment(..., output_dir=output_dir)` 保存实验 JSON。
5. 把结果、实验路径和样例路径写入 `AcceptanceEvidence`。
6. 默认验收样例尽量在 10 秒内运行完毕。

验收器使用临时目录保存检查期间的实验记录，运行结束后自动清理，不会污染正式 `experiments/`。

## 4. 每个自动检查项具体检查什么

| 检查项 | 工具如何检查 | 为什么需要 | 常见修复方式 |
| --- | --- | --- | --- |
| 模块目录 | 检查 `modules/<module_id>/` 是否存在 | 防止代码放错目录或模块 ID 写错 | 按注册表中的模块 ID 建目录 |
| 页面入口 | 导入注册表指定的 `page.py::render` 并确认可调用 | 统一应用必须能加载页面 | 修复导入错误并保留无参数 `render()` |
| 真实页面 | 检查页面是否仍调用公共占位渲染器 | 占位页能打开，但不代表模块已开发 | 实现输入、参数、运行、结果和错误提示 |
| 算法文件 | 检查本组 `algorithm.py` | 防止把全部算法写进页面或仍无算法 | 将业务逻辑放入本组算法文件 |
| 模块 README | 检查“方法、数据、运行、限制”四个小节 | 保证他人能理解和复现 | 补齐对应标题和实际命令 |
| 正常与错误测试 | 至少发现两个测试，并包含错误/非法输入类测试名 | 只测成功路径容易隐藏输入问题 | 增加正常样例和非法输入测试 |
| 验收入口 | 导入并执行 `run_acceptance()`，检查返回类型 | 证明算法确实能在统一环境运行 | 按模板返回 `AcceptanceEvidence` |
| 模块标识 | 比较 evidence、`task_type` 和注册模块 ID | 防止结果被保存到错误任务下 | 统一使用固定模块 ID |
| 小型样例 | 检查样例存在且单文件不超过 10 MB | 默认检查不能依赖大数据或网络下载 | 提供精简、可公开的小样例 |
| 运行时间 | 记录验收样例耗时，默认上限 10 秒 | 避免每次检查都触发长训练 | 缩小样例或使用轻量参数 |
| 实验 JSON | 读取 JSON，检查固定字段、任务和算法标识 | 保证实验可追溯和可比较 | 使用 `save_experiment()` 保存 |
| 文件安全与大小 | 检查密钥后缀、`.env` 和超过 10 MB 的文件 | 防止泄露凭据或误交大数据 | 删除凭据，改用示例配置和下载说明 |
| 中期测试覆盖 | 检查至少四个测试并包含 contract、experiment 类测试 | 确保结果合同与实验保存不是口头承诺 | 增加对应命名和断言的测试 |
| 中期方法数量 | 统计验收结果中的不同 `algorithm` | 至少一种基础方法必须真实可运行 | 将方法加入 `run_acceptance()` |
| 最终方法数量 | 要求至少两个不同 `algorithm` | 最终结果需要可比较的两种方法或策略 | 返回两种真实运行结果 |
| 数据集卡 | 检查模块目录中的 `DATASET_CARD.md` | 数据来源、许可、字段和真值必须可追溯 | 使用公共数据集卡模板填写 |
| 最终实验说明 | 检查 README 是否说明“指标”和“失败案例” | 防止只展示最好结果而不说明限制 | 补充指标条件、失败案例和局限性 |

## 5. `PASS`、`BLOCKED` 和 `REVIEW` 分别表示什么

- `PASS`：该自动检查通过。
- `BLOCKED`：至少一个必需自动检查失败。报告会列出具体失败项，修复后重新运行即可。
- `REVIEW` 或 🔎：需要人工查看，不会被程序静默当成已经确认。

检查单个模块时，自动门禁通过需要：

1. 该模块没有自动失败项；
2. 全量 Pytest 测试通过。

检查全部模块时，自动门禁通过需要：

1. 8 个模块都没有自动失败项；
2. 全量 Pytest 测试通过。

因此，一个尚未开发的组会使全平台检查显示 `BLOCKED`，这只是当前完成度的真实反映，不表示验收工具或 Python 环境损坏。

## 6. 为什么还需要人工复核

以下内容不能仅靠文件名或程序输出可靠判断：

| 人工复核项 | 需要确认的内容 |
| --- | --- |
| 页面语义 | 输入、参数和输出是否易懂；错误消息是否能指导用户处理问题 |
| 数据合规 | 数据来源和许可是否真实；是否含敏感信息；真值或标签如何得到 |
| 指标适用性 | 是否确有真值；指标公式是否适合任务；有没有选择性报告 |
| 方法真实性 | 是否真实运行论文或基线代码；有没有把写死结果当作复现 |
| 结论边界 | 是否区分候选、异常分数和已确认错误；是否夸大实验结论 |

人工复核记录至少写明复核人、日期、操作步骤、发现的问题和处理结论。

## 7. 报告和退出码

默认报告保存在 `reports/acceptance/`，同时生成 Markdown 和 JSON：

- Markdown 供学生和评审阅读；
- JSON 供脚本、CI 或汇总工具读取。

退出码：

- `0`：自动门禁通过；
- `1`：存在自动失败项或全量测试失败。

`--skip-tests` 只适合快速定位模块结构问题，正式提交检查不能使用，因为它跳过了全量回归测试。

## 8. 推荐排查顺序

当报告为 `BLOCKED` 时，按以下顺序修复：

1. 先修导入错误、占位页面和缺失文件。
2. 再让小型样例返回合法 `AlgorithmResult`。
3. 接入实验 JSON，并确认算法和任务标识一致。
4. 补正常、非法输入、合同和实验保存测试。
5. 最后补数据说明、指标、失败案例和人工复核记录。

Pytest 的具体测试内容见 `docs/TESTING_GUIDE.md`。
